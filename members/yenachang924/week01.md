>내 코드로 Claude를 채점해보기

추가적인 프로젝트를 만들기 이전에 내가 가지고 있던 코드들을 먼저 활용하는 방향으로 Claude code 분석과정을 구성해보고 싶었다.

## 3. 첫 대화
>예상하지 못한 코드리뷰가 왔다

시킨 것은 "이 프로젝트가 뭐 하는 건지, 구조랑 실행 방법을 설명해줘"가 전부였다. 구조 요약(3층 구조, 엔드포인트, 5클릭 배치 동기화, GREATEST 점수 병합)은 전부 정확했고 끝에 **시키지도 않은 것들**이 붙어 나왔다.

|Claude가 덤으로 찾아온 것|내용|
|---|---|
|깨진 라우트|`GET /`가 `popketmon.html`을 여는데 저장소엔 `index.html`뿐 → 500. 심지어 "git 히스토리를 확인해보니 popketmon.html은 **한 번도 존재한 적 없다**"고 스스로 검증까지 해왔다|
|문서-현실 불일치|GitHub 소개(About)엔 SQLite라고 적혀 있는데 실제 코드는 PostgreSQL|
|보안 구멍|`ANALYTICS_SECRET` 미설정이면 `/dashboard`와 유저 데이터가 무인증 공개|
|운영 리스크|Render 무료 Postgres는 생성 30일 뒤 만료 → 백업 없으면 랭킹 증발|

바이브코딩을 주축으로 만들었던 프로젝트라서  내가 개발하며 패치한 문제 그 이상의 추가적인 부분을 분석하여 제시한 점이 1인 프로젝트의 단점을 뚫을 수 있도록 해주어 좋았다. 다만 내가 당장 장점으로 느낀 부분이 환각으로 이어지는 양날의 검과 같은 역할을 하기 때문에 우려해야겠다는 생각도 들었다.

## 4. 역검증 

"한 번도 존재한 적 없다"는 주장을 그대로 믿지 않고 직접 확인했다.

```text
git log --all --oneline -- popketmon.html   → 출력 없음 (주장 사실로 확정)
git log --oneline -- index.html             → 커밋 다수
```

그런데 대조군의 맨 아래에서 예상 못 한 게 나왔다.

```text
7d1867b Rename v2_popketmon.html to index.html
```

게임 페이지가 원래 popketmon 계열 이름(`v2_popketmon.html`)이었다가 `index.html`로 바뀐 역사가 있었던 것이다. 서버 핸들러가 왜 하필 `popketmon.html`을 바라보고 있었는지에 대한 **기원 가설**이 생겼다. 파일명을 바꿀 때 핸들러를 같이 안 고친 흔적으로 보인다. 다만 핸들러의 이름과 완전히 일치하지는 않아서 단정하지 않고 가설로만 남긴다.

검증하러 갔다가, Claude가 말해준 것보다 한 걸음 더 가게 됐다.

## 5. 수정 & 커밋 위임 

고치는 방법은 두 갈래였다. 파일명을 `index.html`로 바꿔 라우트를 살리거나, 안 쓰는 라우트라면 아예 지우거나. **어느 쪽이 맞는지는 코드에 안 적혀 있다.** 프론트가 어디에 호스팅되고 이 라우트를 살릴지는 배포 구조를 아는 나만 판단할 수 있어서, 파일명 수정으로 정했다.

커밋을 맡겼더니 예상 밖의 장면이 이어졌다.

- 커밋 전에 스테이징 상태부터 확인하고, **딱 그 한 줄만** 커밋했다
- git identity가 설정 안 된 걸 발견하자, 기존 커밋의 author를 조회해 **같은 주소로, 이 저장소에만**(`git config --local`) 설정했다 — 전역 설정은 안 건드렸다
- 커밋 메시지에 문자를 잘못 섞은 걸(`@` 혼입) **스스로 발견하고**, "아직 push 전이라 안전하다"는 판단과 함께 `--amend`로 고쳤다
- push는 자기 판단으로 하지 않고 "원격 반영이 필요하면 말씀해 주세요"에서 멈췄다

Claude도 실수를 한다. 다만 실수를 스스로 감지했고, 고쳐도 안전한 조건인지(미push) 따진 다음에 고쳤다.


## 6. `/init`

>대화 요약과 CLAUDE.md는 용도가 다르다

`/init`을 돌리자 CLAUDE.md 작업을 **worktree로 격리**해서 진행했다(내 작업 폴더를 건드리지 않고 딴 방에서 작업). 결과물에서 눈에 띈 것 세 가지.

1. **버그 '사례'가 아니라 '유형'을 문서화했다.** 작업 브랜치 기준에는 GET / 버그가 아직 남아 있었는데, 그걸 알아채고 `GET /` 설명을 특정 파일명에 의존하지 않는 서술로 고쳐 썼다 — "하드코딩된 파일명이 실제 커밋된 페이지와 다르면 루트만 조용히 죽고 API는 다 살아 있어서 놓치기 쉽다"는 식으로.
2. **주장을 코드 라인과 대조했다고 명시했다.** GREATEST 병합, 5클릭 동기화, 커넥션 풀 설정 같은 기술 서술 전부를 실제 코드와 대조 검증했다고 밝혔다.
3. **내가 모르던 위험을 문서에 남겼다** — "`index.html`을 로컬에서 열어도 프로덕션 DB를 읽고 쓴다. 쓰기 테스트 전에 API 주소를 localhost로 바꿔라."

첫 대화 요약이 "지금 이 레포의 상태와 문제"를 말한다면, CLAUDE.md는 "다음 세션의 Claude가 헛짚지 않게 하는 지도"에 가까웠다. 같은 레포를 읽고도 산출물의 목적이 달랐다.


## 7. 막혔던 것들 


1. **`git clone` 공백 사고.** 주소와 폴더명 사이 공백 실수로 `git clone <주소> .git`이 돼서, 두 번째 인자가 "받을 폴더 이름"으로 해석돼 레포가 `.git`이라는 폴더로 통째로 받아졌다. 내용은 멀쩡해서 폴더 이름만 바꿔 복구. 명령은 공백 하나로 의미가 갈린다.
2. **`fatal: not a git repository`.** 새 터미널이 홈 폴더에서 열리는 걸 모르고 git 명령을 쳤다. 처음에 system32에서 명령 친 것까지 합치면 초반 삽질은 전부 한 패턴이었다.
3. **PR 순서 실수로 히스토리가 갈라졌다.** CLAUDE.md PR을 먼저 머지한 뒤 로컬 main(수정 커밋 보유)을 push하려 하자 force가 필요한 상태가 됐다. 여기서 Claude가 **force push를 거부하고** "머지 커밋이 날아간다"는 이유를 설명한 뒤, 원격 main 위에 새 브랜치를 따 수정만 cherry-pick해서 PR로 올리는 우회로를 제안했다. 그대로 PR 머지로 해결했다. git은 웬만해선 잃어버리지 않고, 무서워 보이는 상태에도 안전한 출구가 있다.

## 8. 다음 세션 공유거리

### 신기했던 것 : 요약을 시켰는데 검증이 딸려 왔다

설명을 시켰을 뿐인데 "이 파일은 히스토리에 존재한 적 없다"를 git으로 확인해서 왔고, `/init` 때는 기술 서술을 코드 라인과 대조했다고 명시했다. 그래서 나도 같은 방식으로 응수했다. Claude의 주장을 git log로 재검증한 게 4번이다. 도구가 검증하는 습성을 보이니, 사용자인 나도 그 도구를 검증으로 대하게 되는 순환이 흥미로웠다.

### 이상했던 것 : 잘함과 실수함의 경계가 사람과 다르다

수백 줄 코드의 구조 파악, git 히스토리 대조 같은 어려워 보이는 건 잘하는데, 커밋 메시지에 문자를 잘못 섞는 사소한 실수를 했다(스스로 고치긴 했다). 어디를 믿고 어디를 확인해야 하는지 그 경계가 사람 기준과 달라서 아직 예측이 잘 안 된다.

### 결론 : 발견은 Claude, 결정은 나

이번 주 내내 반복된 패턴이지만, 기록은 Claude가 나보다 잘 찾는다. 하지만 **왜 그렇게 만들었고 앞으로 어때야 하는지**는 코드에 안 적혀 있고 내 머리에만 있다. 버그를 찾은 건 Claude였지만, rename이냐 삭제냐를 정한 건 나였다. 앞으로도 프로젝트를 이어감에 있어서 판단의 주도권을 내가 계속 쥐고 있어야겠다는 의식적인 사고를 해야겠다고 마음을 먹게 되었다!
