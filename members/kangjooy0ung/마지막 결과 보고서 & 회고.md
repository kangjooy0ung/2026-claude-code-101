## 1. 무엇을 만들었나

오버워치 팀 슈팅에서는 "메타를 모르면 픽부터 진다"는 말이 있습니다. 경쟁전에서 이기려면
**지금 이 패치·랭크·서버에서 어떤 영웅이 강한지** 아는 것이 가장 빠른 길인데, 정작 그 정보는 흩어져 있습니다.

| 문제 | WatchMeta의 해결 |
| --- | --- |
| 메타 사이트와 전적 사이트가 따로 놀아 창을 여러 개 띄워 비교해야 함 | 배틀태그 입력 한 번으로 전적 분석 + 메타 확인을 **한 화면에서** |
| 광고 많고 데스크탑 위주라 매칭 대기 중 폰으로 보기 불편 | **모바일 우선 UI** |
| "지금 내 랭크" 기준 데이터를 짚어주는 곳이 드묾 | 서버·랭크를 바꾸면 해당 구간 실데이터로 **티어 즉시 재계산** |

**타겟 유저**: 오버워치를 즐겨 하며 경쟁전 티어 상승에 진심인 유저

### 핵심 기능 4가지

1. **메타 티어표** — 역할군(탱/딜/힐)별 S~D 티어, 서버·랭크 필터
   - 블리자드 공식 영웅 통계 페이지 데이터 기반
   - `메타 점수 = 승률 정규화값 × 0.5 + 픽률 정규화값 × 0.5`
   - 점수 순위를 `S 15% / A 25% / B 30% / C 20% / D 10%` 비율로 분포 분할
2. **전적 검색 & 프로필** — 배틀태그로 경쟁전 티어·플레이타임·승률·KDA·모스트 영웅 조회, 영웅 선택 시 세부 기록으로 드릴다운
3. **전장별 영웅 승률** — 맵을 고르면 내 티어 구간에서 그 맵에 강한 영웅을 픽률·승률로 제공 (사용자 반응이 가장 좋았던 기능)
4. **패치노트** — 최신 밸런스 변경 사항을 카드로 정리

### 아키텍처 — 데이터 성격에 따른 요청 방식 분리

- **전적·프로필** (변동성 큼): 매 검색마다 최신 데이터가 필요 → Express 백엔드가 **OverFast API를 실시간 프록시 호출** (보안·CORS 문제 해결)
- **메타 티어표** (변동성 작음): 빌드 시점에 정적 파일(`heroRates.ts`)로 **번들링** → 불필요한 API 호출 제거, 지연 없는 렌더링

사용자 브라우저 ──▶ Frontend (Vercel) ──▶ Backend (Express/Render) ──▶ OverFast API
└··▶ heroRates.ts (빌드 시점 정적 번들, 요청 없음)

## 2. 어떻게 Claude Code를 활용했나

이번 프로젝트는 Claude Code를 **페어 프로그래머**처럼 활용해 만들었습니다.

- **버그 추적**: 코드만 보지 않고 **git 히스토리까지 함께 추적**해 원인을 좁혀나감
- **검증 루프**: 수정할 때마다 **실제 화면을 스크린샷으로 찍어 확인한 뒤에만** 반영
- **발표 자료도 Claude Code로**: 실제 사이트 화면과 데이터를 그대로 가져와 발표 슬라이드 제작

### 트러블슈팅 — "완벽한 답보다, 원인을 좁혀가는 과정"

**CASE 01 · 데이터 정합성**
8/12 넥슨 한국 서버 이관 이후 공식 통계 API가 europe / americas / asia 세 지역만 지원하게 되어
한국 서버 데이터를 받을 수 없게 됨.
→ ❌ 임의의 가짜 수치로 채우기
→ ✅ "데이터 없음"을 투명하게 명시하고 아시아 서버를 대체재로 제공해 신뢰성 유지

**CASE 02 · 이미지 로딩 안정화**
이미지가 한꺼번에 몰릴 때를 대비해 8초 타임아웃을 걸었으나, 응답이 살짝만 느려도
`<img>`가 언마운트되며 요청이 취소돼 영구히 대체 문구에 멈추는 부작용 발견.
→ ❌ 8초 후 요청 취소 + 재시도 없음
→ ✅ 타임아웃 제거, 스켈레톤 UI로 로드될 때까지 자연스럽게 전환

## 3. 6주간 워크플로우가 어떻게 바뀌었나

- 처음엔 막연한 요청("이거 고쳐줘")을 던졌지만, **구체적인 기준을 줄수록 결과물이 좋아진다**는 걸 체감
- "코드 → 스크린샷 확인 → 반영" 루프가 자리 잡으면서, 화면으로 검증하지 않은 변경은 신뢰하지 않게 됨
- 버그가 생기면 현재 코드뿐 아니라 **git 히스토리를 근거로 회귀 원인을 찾는** 습관이 생김

## 4. 사용자 검증

숫자 지표는 아직 없지만, 주변 오버워치 유저들에게 직접 배포해 실사용 반응을 확인.
커뮤니티 글은 추천만 달리고 피드백이 없었는데, 지인들에게선 오히려 더 구체적인 피드백을 받음.
특히 **전장 승률 페이지**가 픽창에서 실질적인 판단 근거가 되어 유용하다는 공통 반응.

## 5. 배운 점 & 아쉬운 점

**배운 점**
- 막연한 요청보다 구체적인 기준(수치, 비율, 예시)을 줄수록 협업 품질이 올라간다
- 없는 데이터를 지어내지 않고 "없음"을 투명하게 드러내는 것이 서비스 신뢰의 기본
- 외부 API 의존 서비스는 데이터 소스 변경(서버 이관 등) 리스크를 항상 염두에 둬야 한다

**아쉬운 점**
- 슬라이드 번호처럼 **서로 기준이 다르면 소통이 헷갈릴 수 있다**는 점 — 공통 기준 합의가 먼저다
- 정량 지표(사용자 수, 리텐션) 기반 검증까지는 못 감
- 패치 버전 필터가 UI만 있고 실데이터 연동 전 상태로 남음
