## 프로젝트: Kinly — 가족 건강 동반자

> 📎 기획서 전체: [Notion](https://cookie-moonstone-7ce.notion.site/369a44f2e1e3807282cbc0b6c657396e)

3주차에 웹앱 전환과 그룹·초대 화면까지 끝냈고, 4주차는 핵심 3기능 중 **①비상 정보 금고를 실제로 쓸 수 있는 상태**까지 올리는 주였다. 서버 PIN·금고 토큰, 화면 전체, 그리고 이 둘이 돌아갈 **실배포 환경**이 동시에 필요했다.

그래서 이번 주의 가장 큰 변화는 기능이 아니라 **작업 방식**이다 — 세션 하나가 순차로 하는 대신 **Claude Code 세션 3개를 동시에 굴리는 병렬 3트랙 체제**로 바꿨다(배포 / 금고BE / 비상정보FE + 조율 세션 1개).

저장소는 실제 의료·비상 정보를 다루는 프로젝트라 **개인 private 레포**(`InSooBeen/kinly`)로 운영 중입니다. 코드 열람이 필요하시면 별도로 초대해 드릴 수 있습니다.

## 일별 진행 상황

### 1일차 · 2026-08-03 — 병렬 3트랙 전환

- 병렬화 준비(Phase 0)를 끝내고 세 트랙에 세션을 붙였다. 워크트리·DB·포트를 나누는 건 기계적이었고, **진짜 어려운 건 "무엇을 나누느냐"가 아니라 "무엇을 공유하느냐"**였다 — 세 세션은 서로의 미커밋 변경을 볼 수 없고 `HANDOFF.md`는 gitignore라 워크트리에 딸려오지도 않는다. 커밋과 무관하게 즉시 보이는 매체가 GitHub 이슈뿐이라, 조율 이슈 #37을 만들고 "작업 시작 / 게이트 통과 / PR 직전" 3시점에 반드시 읽는다를 규약으로 못박았다.
- **계약을 확정하기 전에 30분짜리 스파이크를 넣은 게 이 날 가장 값진 판단이었다.** 금고 토큰 검증을 서블릿 필터로 하려던 계획이 실측에서 깨졌다 — 필터에서 던진 예외가 `ExceptionAdvice`에 닿지 않아 응답 봉투가 깨지고, 그러면 프론트의 에러코드 기반 분기가 통째로 무너진다. `HandlerInterceptor`로 교체. 프론트가 화면 3~4개를 만든 뒤 발견했으면 전부 재작업이었다.
- 계약 작성이 내가 준 전제를 여러 개 뒤집었다 — 접근 로그 엔티티는 **호출처 0곳인 죽은 코드**였고, `PATCH`가 부분 수정이 아니라 **전체 교체**였으며, react-query 기본 retry가 금고 403을 2회 재시도해 **PIN 오타 한 번에 잠금 카운터가 3 소진**되고 있었다.
- 배포는 멘토 추천으로 fly.io가 올라왔는데, **ADR 0005가 이미 fly.io를 검토하고 기각한 적이 있었다.** 재검토는 정당하지만 "멘토가 추천해서"로 근거를 대체할 수는 없다고 판단해 다시 조사했고, 진짜 이득이 비용이 아니라 **`*.fly.dev`가 HTTPS를 즉시 준다는 것**(카카오 로그인·Web Push를 막고 있던 게 정확히 도메인·TLS 부재였다)임을 확인해 근거를 새로 썼다.
- **"54/54 통과"가 Gradle 캐시 값이었다.** `:test UP-TO-DATE`로 스킵된 결과를 그대로 인용하고 있었다. `--rerun-tasks`로 재확인 — 숫자는 같았지만 "통과했다"고 말한 근거 자체가 없었던 것이라 함정으로 문서에 남겼다.
- 조율 라운드에서 **내가 건 게이트가 과했고 트랙 쪽이 맞았다.** "Neon 실측 전엔 배포 PR을 머지하지 않는다"고 선언했는데, 그 PR은 설정 코드뿐이라 실측이 실패해도 바뀌는 게 없었다. **실측 결과가 뒤집을 수 없는 것을 게이트로 걸면 뒤 트랙만 막는다** — 정정하고 머지했다.

### 2일차 · 2026-08-04 — 배포 완주

- `fly deploy`가 헬스체크 타임아웃으로 계속 죽었다. 원인은 `openssl rand -base64 64`가 **64자마다 넣는 줄바꿈** — 명령 치환이 끝의 개행만 지우고 중간 개행은 남겨서 Java `Base64.getDecoder()`가 거부하고 있었다. `tr -d '\n'`으로 해결.
- 전날 Neon 실측이 **오염된 상태**로 남아 있었다. 앱 머신을 아예 끈 채로 잰 CU-hour는 트래픽이 원래 0이라 낮게 나오는 게 당연해서, "Hikari `minimum-idle: 0` 설정이 기여했다"를 증명하지 못한다. 앱을 켠 채로 30분 재측정 → **compute Idle, 누적 0.15 CU-hour**(월 환산 약 4.5, 무료 한도 100의 5% 미만)로 게이트 통과. 측정 오염은 "무엇을 쟀나"가 아니라 **"어떤 상태에서 쟀나"**의 문제였다.
- ADR에 적어둔 재검토 조건은 **아무도 능동적으로 트리거하지 않는다**는 걸 알기 때문에, 상시 가동 재전환·CU-hour 재측정을 문서에만 남기지 않고 **카카오 로그인 이슈(#28)에 직접 물려뒀다** — 실사용이 시작되는 지점에서 반드시 보이도록.

### 3일차 · 2026-08-05 — 금고BE·FE 머지, 실서버 검증

- 배포 → 금고BE(PR #45) → 비상정보FE(PR #51) 순서대로 머지. 조율 세션이 금고BE PR을 **계약 문서와 한 절씩 대조해 직접 읽었다** — 테스트 84개 통과는 "자기 코드가 자기 의도대로 돈다"의 증명이고, 확인해야 할 건 **다른 트랙이 이미 그 계약을 전제로 화면을 만들고 있다는 점**이었다. 계약 변경 0건.
- FE 트랙은 금고BE가 머지되기 전에도 멈추지 않으려고 화면을 먼저 만들었는데, **목킹 레이어를 따로 두지 않고 실제 `vault.ts` 함수를 처음부터 호출**했다(테스트에서만 `vi.mock`). 그 결과 서버가 들어온 뒤 **교체할 목킹 코드가 0줄**이었고, 실서버 검증이 "코드를 바꾸고 확인"이 아니라 "그대로 두고 확인"이 됐다.
- 실서버를 실제로 때려보고 **단위 테스트가 구조적으로 못 잡는 결함 3건**을 찾았다.
  1. **PIN 실패 카운터가 롤백된다**(#52) — 엔티티를 바꾼 뒤 같은 트랜잭션 안에서 예외를 던져 flush가 취소된다. 로직은 맞고 트랜잭션 경계만 틀렸다. 관측 지점이 커밋 경계 너머라 **요청을 두 번 보내야만** 드러난다.
  2. **본문이 깨진 모든 요청이 400이 아니라 500**(#47 계열) — "연락처 PATCH가 500이다"에서 멈췄으면 연락처만 고쳤을 것이다. 원인을 끝까지 밀어서 `ExceptionAdvice`에 핸들러가 없는 **API 전역 문제**임을 알았다.
  3. **연락처 `priority` 중복** — FE가 새 항목 순번을 `contacts.length`로 계산해 중간을 지우면 기존 값과 겹쳤다. `max(priority) + 1`로 고치고 회귀 테스트 추가.
- 헤드리스 크로미움으로 전 흐름을 돌려 계약의 위험 항목을 눈으로 확인(콘솔 에러 0건). **retry 검증은 원래 계획대로는 불가능했다** — 판정 기준이던 `remainingAttempts`가 위 1번 결함 때문에 항상 5로 고정이라, **응답 값에서 요청 횟수로 관측 지점을 옮겨** 같은 질문에 답했다.

### 4일차 · 2026-08-06 — 전역 네비게이션 (진행 중)

- 화면이 다 붙고 나서야 드러난 문제: **금고에 들어가면 나갈 길이 브라우저 히스토리뿐**이었다(#53). 상단바 로그아웃을 각 화면이 슬롯으로 넘기는 구조였는데 실제로 넘기는 화면이 그룹 목록 하나뿐이라, 금고에서는 상단바가 빈 껍데기가 됐다. **탈출구를 각 화면의 책임으로 두면 한 곳만 빠뜨려도 사용자가 갇힌다.**
- 로고를 홈 링크로, 로그아웃을 상단바 상시 노출로 올리고, `navigate(-1)` "뒤로" 버튼은 **목적지가 정해진 링크**로 교체했다(탭을 누른 만큼 되감아야 했고 새로고침 뒤엔 갈 곳이 아예 없었다). 금고 URL이 `/persons/{personId}/...`라 그룹 정보를 갖고 있지 않은 문제는 `?from=` 쿼리로 출발지를 넘겨 해결 — **새로고침·북마크로 열려도 살아남는 폴백**을 함께 뒀다.

## 이번 주에 남은 것

- **계약을 코드로 확정하고, 확정 전에 스파이크로 실측한다.** 두 트랙이 동시에 짜고 있으면 잘못된 전제 하나가 양쪽 재작업이 된다.
- **게이트는 미리 값의 형태로 못박되, 어느 산출물의 게이트인지를 틀리면 안 된다.**
- **통과했다는 숫자보다 그 숫자가 실제 실행 결과인지**를 먼저 본다(캐시된 테스트 결과, 오염된 측정).
- 실서버 검증은 단위 테스트의 중복이 아니라 **관측 지점이 다른 검증**이다 — 이번 주 서버 결함 3건이 전부 거기서 나왔다.
